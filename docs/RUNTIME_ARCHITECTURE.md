# 推理运行时与模型接入

Android、iOS、macOS 与命令行共用 C++ 推理核心。应用层负责下载、文件管理、播放和 UI；Swift、Rust、JNI 等通过 C ABI 调用，模型更新不应要求重写平台界面。

## 代码入口

| 层 | 入口 | 职责 |
|---|---|---|
| 应用接口 | `runtime/include/ortts_engine.h` | 创建、合成、PCM 回调、取消与释放 |
| 引擎包装 | `runtime/src/ortts_engine.cpp` | 资源检查、session 生命周期、线程与请求管理 |
| 共享默认值 | `runtime/src/inference_defaults.h` | CLI 与引擎共用 CPU、session 和采样默认值 |
| CLI | `src/tts_main.cpp` | 离线合成与测量输出 |
| 模型集成 | `vendor/runtime.lock.json`、`vendor/patches/` | 固定 audio.cpp 来源与模型加载补丁 |
| 资源清单 | `models/` | 文件角色、路径、长度与校验信息 |

当前嵌入式接口支持 P3/P5 与发布的 Qwen–LFM 声学链；其他声学架构尚未接入此接口。新的检查点若保持架构和接口不变，只需更新相应权重及可信清单，不应修改平台代码。模型加载仍须保留来源、形状、精度与配套文件绑定校验。

## 兼容方式

优先在同一主线维护多个模型实现，不按平台或检查点建立长期分支。

- 模型包配置分别描述生成端、predictor 和声学端，避免把 P3/P5 与某一个 decoder 绑定。
- 运行时根据经过校验的架构标识选择已编入的实现；未知架构、缺失实现或不兼容接口应在加载前明确报错。不能从文件名、训练步数或 tensor 数量猜测架构，也不能静默使用另一套权重。
- 编译选项决定是否包含某个实现或加速后端，控制依赖和包体积；线程数、音色、模型变体等由运行配置决定。CPU 指令集采用平台构建 profile，模型包不得自行要求执行未检查的指令集。
- 当前 C ABI 的结构大小与版本检查保持不变。将来扩展配置须采用版本化入口或兼容的扩展结构，避免让 Swift/Rust/JNI 直接依赖 C++ 类布局。

架构选择器是后续接入约定，当前接口不会自动识别任意声学模型包。实现新 selector 前需定义并版本化运行时清单，区分其与下载清单及底层模型 manifest 的职责。

## 接入新声学端

统一边界应为生成端输出的 frame-major RVQ codes，以及解码端输出的单声道 FLOAT PCM。每个实现单独拥有状态，提供 reset、push 和 finish；finish 只在真实 EOS 后提交，取消或长度上限不得伪装成 EOS。

模型合同需明确码本数量与范围、帧率、采样率、权重精度、前瞻、缓存、首尾裁切及 OLA 刷新规则。旧实现与新实现可以有不同首块长度，回调时间不等于扬声器首音。

LiquidCodec 原型目前仍在独立实验目录，通过 C++ worker 隔离不同版本的 ggml。移动应用接入前需解决同进程依赖或符号隔离，不能直接把 Linux 的进程启动方式照搬到 iOS。该原型不属于当前正式运行时支持范围。

验证顺序为：权重身份与错误包拒绝、同精度数值与状态边界、同生成端 codes 一致、完整链计时、音频质量。模型接口通过不等于质量通过；decoder-only 速度不等于完整链速度。
