# P3 速度变化与新旧 codec 评估

结论：目前没有证据支持因 RTF 回退旧 LFM 主线。相同男声、同文本、同源码 I8MM 构建下，旧包与 LiquidCodec 热 RTF 分别约0.492和0.495，差异小于逐次波动。保留旧包作为兼容和试听对照，默认继续新版 LC；主线音质选择仍需人工听感，不以接口成功替代。

## 为什么之前低于0.5，这轮却到0.7–0.8

此前记录包含 I8MM 优化版单次女声0.446，以及 baseline单次0.573；这次完整矩阵是 baseline，并已进入 serious 温度状态，文本长度也不同。新旧 `female` 虽然同名，向量 SHA 不同；新版主模型 text embedding由F16变为Q8_0，P3由safetensors路径变为GGUF混合Q8/F16。输出时长和采样轨迹会变。不能把这些数据的差全部归到 codec，也不能给热降频分配一个精确百分比。

补测采用历史同一句：`你好，欢迎使用 OrTTS。本地语音合成，让交流更加自然。`，P3、4线程、seed20261029、关闭播放，一次预热后取三次。每格启动前冷却60秒，额外女声历史文本复测冷却120秒；实际推理时系统均记录fair。男声向量两包逐字节一致。未锁频或随机化，多次持续请求仍有升温趋势。

| 相同男声 | baseline 热 RTF 中位数（范围） | I8MM 热 RTF 中位数（范围） |
|---|---:|---:|
| 旧 LFM 包 | 0.646（0.505–0.666） | 0.492（0.481–0.530） |
| 新 LC 包 | 0.523（0.513–0.533） | 0.495（0.481–0.509） |

新版女声用历史文本的 baseline 复测为0.492（0.452–0.502），同样仍可低于0.5。此行女声并非旧向量，不用于证明 codec 加速比。I8MM两行记录低电量模式关闭；baseline旧版QA未采集该字段，不补造值。fair只是粗粒度温度等级，不意味着频率完全相同。以上是整包比较，生成端资产也变了。[原始逐次记录](../../benchmarks/p3-codec-control-iphone-20261108.json)

## codec 是否增加了主要负担

固定生成端的 Mac 隔离：旧talker、旧P3、旧女声和相同seed，只换codec。六个会话产生的codes哈希全部相同。三个热观察值中位数：旧LFM API RTF0.284、codec阶段207ms；LC API RTF0.280、codec阶段164ms。没有整体大幅退化，差异不足以宣称稳定加速倍数。开启trace，属于流水线诊断，不是纯kernel或功耗排名。[历史原始记录](../../benchmarks/codec-isolation-macos-20261108.json)

真机 LC 男声正常播放总API约2.27s，LC全部阶段累计约235.5ms，其中codec约210.3ms，占总耗时约一成。即使假设旧codec成本为零，LC本身也解释不了整段耗时的大幅差异。这条诊断与固定codes的Mac证据一致，但不能把Mac的阶段倍数外推手机。

高温矩阵的0.73–0.82仍是实际持续负载表现，不能用冷却短句掩盖。当前优化应优先看生成端、CPU指令档位、线程与热预算；暂不优先重写codec。通用应用仍默认安全baseline，I8MM只在支持且验证过的设备部署，不强推到全部ARM64设备。

## 是否保留旧模型为主线

保留旧兼容入口和 `models/`，新版放 `models-liquid/`，不删除也不混接。当前无需因速度撤回LC：同I8MM测试速度接近；P3完整下载从旧包约2.196GB降至新版1.809GB；新版P5中文长句本轮完整回读，旧包对应样本触及40.96s且回读只捕获首句。后两点也不是全面质量认证，尤其不能将下载量等同于峰值RAM。

两个codec相同codes的试听样本保留在本机 `outputs/codec-listen/legacy-lfm.wav` 与 `liquidcodec.wav`，便于只比较声学解码听感。若目标音色在旧codec下听感更好，可以继续选旧包；不要仅凭不同温度/音色的RTF改变默认路线。手机内存峰值和持续功耗还未完成受控采样，不声称已解决。
